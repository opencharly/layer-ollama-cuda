# 2026.320.1042 — fix(pins): advance pod-ollama to v2026.320.1029 in the ollama-cuda backend

## Summary

One line: this candy's `require:` moves `pod-ollama:v2026.274.0620 → v2026.320.1029`,
the tag pod-ollama published when `OLLAMA_VERSION` reached v0.40.16
(opencharly/pod-ollama#8).

This candy is the CUDA backend ADD-ON to the ollama candy, so its `require:` is the
reference that decides which ollama the backend drops `libggml-cuda.so` into. It was
still naming the pre-bump candy.

**It has to move BEFORE any composing box moves, and that is mechanical, not stylistic.**
With this `require:` at the new tag and a composing box still pinning the old one, the
loader refuses the whole project:

```
$ charly box validate            # distro-fedora worktree, cuda layer at the new tag
charly: error: command "validate": validation error: candy
github.com/opencharly/pod-ollama resolved to multiple git tags with differing content
within one scope (box=ollama); using newest referenced v2026.320.1029
(from github.com/opencharly/pod-ollama@v2026.320.1029)
```

So the pins are one cutover with a required order: **this repo's `require:` → this
repo's tag → the composing box moves BOTH of its refs (`pod-ollama` to v2026.320.1029
and `layer-ollama-cuda` to this commit's tag) in one change.** Advancing either side
alone is a red project, which is why the Fedora leg follows rather than accompanies.
